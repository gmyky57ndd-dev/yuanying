# 专业分身：设置与调用

记录于 2026-10-26。想法，不是定稿。

## 问题

元婴现在的分身是「人格分身」——小悟、元婴本体，靠 profile 文件
（identity / voice / values）区分。它们共享同一套记忆、同一套工具、
同一个模型。

但「专业分身」不是人格差异，是**领域能力差异**。一个做 ASO 的分身、
一个做 live2D 的分身、一个做财务的分身，它们需要的是：
不同的知识、不同的工具、不同的调用时机。

人格分身解决「谁在说话」，专业分身解决「谁来做这件事」。

## 需要想清楚的几件事

1. **专业分身是什么形态**：是 profile 文件的变体，还是独立的
   skill / prompt 包？前者复用现有机制，后者需要新的加载路径。

2. **怎么被调用**：主人手动切换？还是元婴判断任务类型后自动路由？
   自动路由需要一套分类规则，容易错；手动切换可靠但打断。

3. **记忆边界**：专业分身读不读主人的全部记忆（signals、notes、
   conversations）？做 ASO 的分身不需要知道睡眠数据，但需要知道
   项目历史。记忆要按领域切片，还是全量共享、靠 prompt 约束？

4. **工具边界**：专业分身是否只能调用领域相关的工具？比如财务分身
   不该有 push_to_dev。

5. **和模型路由的关系**：现有模型是请求级、全局的（ES-029），
   不按分身切换。专业分身如果要换模型（比如代码用另一个），
   就得打破这个设计，或者让专业分身自带模型偏好。

## 一个可能的方向

专业分身 = profile（人格/语气）+ skill 包（领域知识 + 工具白名单 +
可选模型偏好）。调用走手动切换，先不做自动路由——自动路由的
错误成本比手动切换的打断成本高。

记忆全量共享，靠 skill 包的 prompt 约束关注面。先跑起来，再谈切片。

## 待验证

- 现有 profile 机制能否承载 skill 包，还是要新表。
- 工具白名单在请求级过滤，还是靠 prompt 自律。
